# M0: Skeleton and deploy

Status: **in progress** (approved 2026-11-04). Code side done: scaffold,
manifest, capability panel, Actions deploy, Pages enabled with the custom
domain. Node upgraded, DNS live, certificate issued, HTTPS enforced. Waiting on

## Goal

A page at https://japan.garbage.house that loads on the iPhone over HTTPS,
installs to the Home Screen from Chrome, and tells us whether the installed
app has the capabilities M7 will depend on. Every later milestone deploys
through the pipeline this one sets up.

- [x] `npm run dev` serves the page locally on Node 26.
- [x] A push to `main` builds and deploys via GitHub Actions with no manual

- [x] https://japan.garbage.house loads with a valid certificate.
- [x] The page shows the git commit it was built from, so we can confirm a

- [ ] Chrome on the iPhone offers "Add to Home Screen", and the installed

- [ ] The page's capability panel, viewed inside the installed app, reports
      standalone mode, service worker support, geolocation API present,

      Chrome-install path we're betting on in `CLAUDE.md`.

## Steps

### 1. Node upgrade (Jerry's machine, done together)

Install nvm-windows 2.x, then `nvm install lts` and `nvm use lts` (Node 26).
Vite 8 needs Node 20.19+ or 22.12+; the machine has 14.

Non-obvious: nvm-windows works by owning `C:\Program Files\nodejs` as a
symlink it re-points on `nvm use`. Its installer detects the existing Node
14 and offers to take it under management, which keeps 14 available as
`nvm use 14`. Anything that depended on the global Node 14 keeps working
after switching back. Each Node version has its own global npm packages.

I'll give the exact commands and wait; I won't change the machine's Node
install unasked.

### 2. Scaffold the Vite project

`npm create vite@latest . -- --template vanilla-ts`, then strip the demo
(counter, logos, demo CSS) down to a blank page. Pin dependency versions in
`package.json` and commit `package-lock.json`.

Files:

```
package.json, package-lock.json
tsconfig.json
vite.config.ts
index.html
public/CNAME              -> "japan.garbage.house"
public/manifest.webmanifest
public/icons/             -> 192 and 512 px PNG, 180 px apple-touch-icon
src/main.ts
src/capabilities.ts       -> the capability panel
src/style.css
```

`vite.config.ts` sets `base: "/"` and injects the short git SHA at build
time via `define`, so `main.ts` can print it. No plugins yet.

Non-obvious: Vite's `base` is the URL prefix for every built asset. On a
GitHub Pages *project* site without a custom domain the app lives at
`/japlanning/`, and `base: "/"` would 404 every script. With the custom
domain the app is at the root. We commit to the custom domain from the start
and verify there, rather than carrying two base paths.

### 3. Manifest and iOS install metadata

`manifest.webmanifest`: name, short name, `display: "standalone"`,
`start_url: "/"`, theme and background colours, 192/512 icons with
`purpose: "any maskable"`. `index.html` gets the viewport meta with
`viewport-fit=cover`, `theme-color`, a link to the manifest, and
`apple-touch-icon`.

Non-obvious: iOS reads `display` from the manifest for Home Screen installs
since 16.4, from any browser. The older `apple-mobile-web-app-capable` meta
is still honoured and harmless, so include it. No service worker in M0; that
is M7, and an empty SW now would only complicate cache debugging later.

Icons: a plain placeholder (a coloured square with "J") generated by a tiny
script, replaced whenever Jerry has something better.

### 4. Capability panel

A few lines in `capabilities.ts` that render a list:

| Check | How |
| --- | --- |
| Standalone | `matchMedia("(display-mode: standalone)").matches` or `navigator.standalone` |
| Service worker | `"serviceWorker" in navigator` |
| Geolocation | `"geolocation" in navigator` (presence only, no prompt) |
| Clipboard | `"clipboard" in navigator && "writeText" in navigator.clipboard` |
| Storage | `navigator.storage.estimate()` quota and usage, and whether `persist` exists |
| User agent | raw string, for telling Chrome from Safari |

Read-only, no permission prompts. It stays on a `/debug` route or behind a
tap on the version string once the real UI exists.

### 5. GitHub Actions deploy

`.github/workflows/deploy.yml`: on push to `main`, checkout, setup-node 26
with npm cache, `npm ci`, `npm run build`, upload `dist/` with
`actions/upload-pages-artifact`, deploy with `actions/deploy-pages`.
Permissions `pages: write` and `id-token: write`. Concurrency group so a
second push cancels an in-flight deploy.

Repo settings, which I'd set with `gh api` after go-ahead: Pages source
"GitHub Actions" (not "deploy from a branch"), custom domain
`japan.garbage.house`, and enforce HTTPS once the certificate exists.

Non-obvious: the Actions deploy mode doesn't touch any branch; `dist/` is
uploaded as an artifact and served directly. The `public/CNAME` file is
what tells Pages which domain the site answers to; without it, Pages drops
the custom domain on every deploy.

### 6. DNS (Jerry, at Squarespace)

One CNAME record: host `japan`, value `jfeng94.github.io`. Add it as early
in M0 as possible since propagation plus GitHub's certificate issuance can
take an hour. Until it resolves, the deploy still succeeds; the site is just
unreachable at the domain.

### 7. Verify on the phone (Jerry)

Open the URL in Chrome on the iPhone, share menu, Add to Home Screen. Open
the installed app and read the capability panel. Screenshot it into the
proposal's results section.

## Out of scope

Data loading (M1), any map (M3), service worker and offline (M7), tests
(start in M1 with vitest), Android or iPad checks.

## Risks

- **Chrome install path doesn't behave as documented.** That's exactly what
  the capability panel is for. If the installed app reports no service
  worker or no standalone mode, M7's plan changes and we find out now, not
  in M7.
- **Certificate issuance lags.** Mitigated by doing DNS first.
- **nvm-windows and the existing Node 14.** If the installer doesn't adopt
  the existing install cleanly, the fallback is uninstalling Node 14 first;
  nothing on this machine is known to need it, but I'll ask before removing.
